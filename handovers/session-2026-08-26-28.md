## 2. WO-7 — M01 Persistence + K8s Infrastructure Hardening (2026-08-27)

**Process note:** Started directly on local `main` without a work order (violates Rule 1).
Regularized as WO-7 in the status log. Commit `18993e1` (32 files, +2384/-74).

### What was built

**M01 (Tenant Control Plane) — PostgreSQL persistence from scratch:**
- New `internal/database/` package: 12 files, 11-table schema (tenants, subscriptions,
  secrets, deployments, environments, namespaces, resources, agents, invoices,
  payment_methods, policies). Complex nested fields stored as JSONB.
- `internal/store/persist.go`: write-through sink. 33 Persist/save/Hydrate functions.
  Every Create/Patch/Update/Delete calls `save()` to PostgreSQL. Failed writes log loudly
  but never fail the request.
- `main.go`: fail-closed if `DATABASE_URL` set but unreachable. `Hydrate*()` reloads all
  11 stores at boot with per-entity load summary.
- `config.go`: `DatabaseURL` from `DATABASE_URL` env var.
- K8s: `DATABASE_URL` wired to `operan-postgresql` ConfigMap `DSN` key.

**M03 (Agent Orchestration) — PostgreSQL enabled in K8s:**
- `DB_MODE=postgres` + connection env vars added to the manifest.
- The existing 18-table PostgreSQL repository layer is now actually used (was in-memory).

**M04/M08 — Pre-existing crash bug fixed:**
- Both referenced a `secret` named `operan-postgres` that does not exist in any manifest.
  Would have crashed with `CreateContainerConfigError` on next deploy.
- Fixed: added `DSN` key to `operan-postgresql` ConfigMap. Both modules switched to
  `configMapKeyRef`.

**K8s — hostPath → PVC:**
- 4 module data volumes (M05, M07, M09, M11) converted from node-local `hostPath` to
  `ReadWriteOnce` PVCs (10Gi each). New `deploy/k8s/persistent-volumes.yaml`.
- `fix-data-perms` init containers removed. Zero `hostPath` references remain in module
  deployments.

**M05 image sha-pinned** to `sha-aaa2d15` in `modules.yaml`. `:latest` would un-pin the
cluster to whatever was last pushed to the registry.

**ops-all-001 dropped from flagship array** in portal `departments.js`. The template has
0 capability steps; rendering it as flagship with an outline-gated deploy button was a
semantic collision.

### Verification

- M01: `go build ./...` ✅, `go vet ./...` ✅, `go test ./... -race -count=1` ✅
- K8s: YAML validates (18 + 4 + 3 docs), zero `hostPath` refs, no missing secret refs

### Issues found and fixed during deploy

1. **ARM vs amd64** — First build was for Apple Silicon (M1/M2/M3). Cluster is x86_64
   (adri-ai-01). `ImagePullBackOff: no match for platform in manifest`. Rebuilt all 7
   with `--platform linux/amd64`.

2. **M03 missing pgx driver** — `internal/database/database.go` uses `database/sql` but
   never imports `github.com/jackc/pgx/v5/stdlib` to register the `pgx` driver. Crashed
   with: `sql: unknown driver "pgx" (forgotten import?)`. Fixed with blank import
   (commit `42fec95`). Rebuilt, pushed, redeployed.

3. **M03 missing database** — The `orchestration` database did not exist in PostgreSQL
   (only `operan` existed). Created it: `CREATE DATABASE orchestration;`. M03's
   migrations then ran on first boot, creating the 18 tables.

4. **M04/M08 missing secret (live cluster)** — The live deployments referenced
   `secret/operan-postgres` (does not exist in any manifest). `kubectl apply` failed
   with 3-way merge conflict (`value` vs `valueFrom` on same env var). Fixed with
   direct `kubectl patch` to `configMapKeyRef/operan-postgresql/DSN`.

5. **`DSN` key missing from live ConfigMap** — The `operan-postgresql` ConfigMap had
   5 keys (POSTGRES_DB, USER, PASSWORD, HOST, PORT) but no `DSN`. Added via
   `kubectl patch configmap`.
